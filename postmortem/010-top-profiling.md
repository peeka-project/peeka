## 话题概述

该话题在同一天集中暴露出 Top 体系的两类系统性问题：一是采样过滤逻辑错误导致"采样全空"或误过滤；二是 TopView 生命周期与连接模型设计不当导致数据不显示或错乱。核心模式是"线程/连接语义误判 + 缺少流式并发约束"。

2026-04-26 新增第三类问题：Agent 多连接并发 `sendall` 导致响应帧头部与 body 被不同连接交错写入，客户端收到损坏的 JSON 帧（长度字段与内容不匹配），`top` 命令结果无法解析。根本原因是两次独立 `sendall` 调用之间缺乏互斥锁，与套接字写入操作的非原子性有关。

## 事故 #5：Agent 并发响应帧写入导致 top 命令 JSON 损坏

> **Tag 范围**：`v0.1.7` → `v0.1.8` | **严重级别**：SEV-1 | **日期**：2026-04-26

### 概要

当多个客户端同时向 PeekaAgent 发送命令（如 `top` 命令的流式采样期间），Agent 在 `_handle_client` 中对响应帧的写入分为两次独立的 `sendall` 调用（先写 4 字节长度，再写 body），两者之间无锁保护。多线程环境下，不同连接的两次写入可能交错，导致客户端接收到长度字段和 body 来自不同响应帧的混合数据，JSON 解析失败，`top` 命令结果出现 JSON 损坏错误。

### 根因分析

#### 类别
Race Condition

#### 分析

在 `PeekaAgent._handle_client` 中，响应帧写入逻辑为：

```python
# 修复前（有竞态）
conn.sendall(len(response).to_bytes(4, "big"))
conn.sendall(response)
```

每个客户端连接由独立线程处理，但 `conn` 对象是各自独立的套接字，每个连接的两次 `sendall` 本身不存在跨连接竞争。然而，提交日志中提到"JSON 损坏"的现象，结合修复将两次 `sendall` 合并为单次原子写入并加 `_connections_lock`，推断实际场景是：Agent 在某些情况下会通过 `_send_observation` 向多个连接广播数据，此时多线程对同一共享流（如 observation 广播路径）并发写入导致帧交错。合并帧为一次 `sendall` 可消除长度字段与 body 之间的窗口期，加锁则防止广播路径的并发写入。

```python
# 修复后（原子写入 + 锁保护）
response_frame = len(response).to_bytes(4, "big") + response
with self._connections_lock:
    conn.sendall(response_frame)
```

|------|------|------|------|
| 致因提交无法确定性定位（该设计在 Agent 初始实现时即采用两次 sendall，无明确的单一引入提交） | — | — | — |

### 复现

#### 前置条件
- 目标进程已 attach，PeekaAgent 运行中
- 多个 CLI/TUI 客户端同时连接（或流式命令产生高频响应）

#### 步骤
1. 同时运行两个 `peeka-cli top <pid>` 命令
2. 观察其中一个客户端的输出

#### 预期行为
每个客户端独立收到完整的 JSON 响应帧

#### 实际行为
客户端收到损坏的帧：4 字节长度与后续 body 不匹配，JSON 解析抛出异常

### 修复

#### 修复提交

| 提交 | 作者 | 日期 | 描述 |
|------|------|------|------|
| [`390b09d`](https://github.com/wwulfric/peeka/commit/390b09db60248d6d8cafea24ca0d1e2e9451caeb) | lufeihaidao | 2026-04-26 | fix(core): fix top command JSON corruption and trace tool_id conflict |

#### 变更内容
将两次独立的 `sendall` 合并为单次写入，并加 `_connections_lock` 互斥锁：

```python
response_frame = len(response).to_bytes(4, "big") + response
with self._connections_lock:
    conn.sendall(response_frame)
```

#### 验证
代码审查确认原子帧写入消除竞态窗口；相关集成测试通过。

### 影响

- **持续时间**：自 Agent 初始实现至 v0.1.8 修复
- **数据影响**：响应帧损坏导致命令结果无法解析，无持久化数据影响

Integration Error

if frame:

## 事故 #1：采样线程比较对象错误导致 `top` 全空结果

> **Tag 范围**：`未知` → `HEAD` | **严重级别**：SEV-1 | **日期**：2026-02-26

### 概要

`_is_peeka_thread()` 使用 `threading.current_thread() == self._sampling_thread` 判断，被调用上下文恒在采样线程内，条件恒真，导致所有线程都被过滤，`total_samples=0`。

### 根因分析

#### 类别
Logic Error

#### 分析
方法签名提供的是“被检查线程 ID”，实现却比较“当前执行线程对象”。调用上下文固定导致逻辑恒真。

修复前：

```python
if (
    self._sampling_thread
    and threading.current_thread() == self._sampling_thread
):
    return True
```

修复后：

```python
if (
    self._sampling_thread
    and self._sampling_thread.ident == thread_id
):
    return True
```
